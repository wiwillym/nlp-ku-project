7. What survives a Colab disconnect/restart
This is the part beginners most often get burned by:
   * Colab's local disk (where you git clone to) is 100% temporary. When the runtime disconnects, restarts, or times out (idle ~90 min, or hard limit ~12 hrs), everything on that disk is wiped — your clone, any new files, any uncommitted edits. Gone.
   * The GitHub repository is permanent. Anything you git push is safe forever, on GitHub's servers, independent of Colab.
   * Google Drive (if mounted) is also permanent, but it's not "connected" to GitHub automatically — it's just another disk.
The rule that follows from this: commit and push before you close your laptop or your session goes idle. If you don't push, your work only exists in a runtime that can vanish.

10. The four "places" — what's actually different about them
   * GitHub repository: the permanent, shared source of truth. Lives on GitHub's servers, not on any single person's machine.
   * Colab runtime: a temporary virtual computer Google gives you for the session — has its own disk, its own Python, its own everything. Wiped when the session ends.
   * Google Drive: your personal permanent cloud storage. Not inherently connected to Git — you can choose to clone a repo into a Drive folder so the clone itself persists, but Drive doesn't know about Git branches, commits, or GitHub.
   * Local filesystem inside the runtime (e.g. /content/your-repo): the disk inside the temporary Colab machine. This is where your git clone actually lands. Temporary unless you git push (to GitHub) or explicitly copy files to Drive.

12. Quick concept glossary (only what you need)
   * Repository (repo): a project's folder, tracked by Git, with full history of every change.
   * Clone: downloading a full copy of a repo onto a machine (here, the Colab runtime).
   * Commit: a saved snapshot of your changes, with a message describing what changed.
   * Push: upload your commits from your local clone to GitHub.
   * Pull: download commits your teammates pushed, into your local clone.
   * Branch: a parallel, isolated copy of the codebase so you can work without disturbing main or your teammates.
   * Pull Request (PR): a request to merge your branch's changes into main, usually after a teammate reviews it.
   * sys.path: the list of folders Python searches when you write import something. Adding src/ to it is what lets notebooks "see" your .py files.
   * requirements.txt: a plain text list of Python packages (and versions) the project needs; pip install -r requirements.txt installs all of them at once.

   * A README — often has exact setup instructions your teammate already wrote; read it before improvising.

No — nothing syncs automatically, in either direction. Think of it as three separate, disconnected copies:
GitHub (permanent)  ←—— you must push ——  Colab's clone (temporary)


   * Editing a cell in Colab, running code, saving the .ipynb — none of that touches GitHub. It only changes the file sitting on Colab's temporary disk.

So the mental model is: your Colab clone is a snapshot, frozen at the moment you cloned it. It drifts out of sync with GitHub (and with your teammates) until you deliberately sync it in one direction or the other.
What "change → save" actually looks like in practice
   1. You edit src/preprocessing.py or a notebook cell in Colab.
   2. You test it, it works.
You save it to GitHub:
!git add .!git commit -m "Fix tokenizer bug"!git push origin yourname-feature
   3.    4. Only now does the change exist on GitHub — visible to your teammates, and safe even if the Colab runtime dies five minutes later.
The trap to watch for
If you forget step 3 and your runtime disconnects (idle timeout, browser closed, "Runtime → Restart"), your edits are gone — they only ever existed on that temporary disk. This is the single most common way people lose work in this kind of setup, so it's worth building the habit: commit + push before you stop working, not just at the very end of a session.
And the reverse matters too — if a teammate pushes a fix to preprocessing.py while you're mid-session, your notebook keeps using the old version in your local clone until you git pull. If something behaves unexpectedly, pulling the latest code is often the first thing to try.

A:
Good questions — this is where the "temporary vs. permanent" distinction really matters. Let me untangle each one.
Where do you run the git commands?
In a code cell of a Colab notebook — any notebook, opened normally (File → New notebook, or open an existing one). You don't need anything special to "start"; you just need a notebook open, because Colab's code cells are your only way to run commands on the runtime. Each command is a line like:
!git add .
!git commit -m "Add tokenization step"
!git push origin yourname-feature


The ! tells Colab "run this as a terminal command," not Python code.
Do these commands get "saved"? — this is the key distinction
There are two completely different things here, and it's easy to mix them up:
   1. The notebook file itself (the .ipynb with your cells, including the git commands you typed) — yes, this can be saved, either to Google Drive (File → Save) or back to GitHub (File → Save a copy in GitHub). Saving it just preserves the text of what you typed, like a recipe.
   2. The effect of running those commands — i.e., the actual cloned repo folder, the files you edited, installed packages — this lives on the temporary runtime disk and is wiped when the session ends, regardless of whether you saved the notebook.
So: saving the notebook does not mean you can skip re-running git clone next time. The commands are saved as text; the results of running them are not. Each new session, you re-run the clone/checkout/install cells from scratch — that's normal and expected, and only takes a few seconds.
(The one thing that genuinely does persist without re-doing anything: files actually pushed to GitHub. Those are safe forever, independent of Colab.)
Do you need to open a notebook first, and add the secret every time?
Notebook: yes — open any Colab notebook (new or existing) to get a runtime to type commands into. It doesn't have to be one of your project's actual notebooks; some people keep one small "setup" notebook just for cloning/pushing, separate from the analysis notebooks.
Secret: here's good news — the secret persists across sessions and notebooks automatically. It's tied to your Google account, not to a single notebook or runtime. You add it once (🔑 icon → Add new secret → GH_TOKEN), and every future Colab notebook you open can access it with userdata.get('GH_TOKEN') — you just need to toggle "notebook access" on for that particular notebook the first time you use it there. You won't need to regenerate or re-paste the token itself.
What happens to a "created file" (e.g., a new .py file you added in src/)?
Same rule as everything else on the runtime disk:
   * If you create it, edit it, run it — it exists only on the temporary Colab disk.
   * If the session ends without you pushing it — it's gone, permanently, no recovery.
   * If you git add / git commit / git push it before the session ends — it now lives on GitHub, safe forever, and will be there the next time anyone (including you) clones the repo.
So the practical habit: treat "push" as your save button. Nothing you do in Colab is truly saved until it's on GitHub (or, for the notebook file specifically, until you've saved a copy to Drive/GitHub via the File menu).

Shows the exact line-by-line changes inside modified files — lines added (+) and removed (-). Use this to actually review what changed, not just that it changed. If something looks wrong (e.g. you accidentally deleted a function), fix it before committing.

3. What if it refreshes before you save?
This is the real risk, and the honest answer is: anything genuinely uncommitted is unrecoverable. There's no undo, no trash bin — the disk is just gone. So the defense isn't a recovery trick, it's a habit:
   * Commit + push in small chunks, often — not just once at the end of a multi-hour session. E.g. after finishing one function, one preprocessing step, one working cell — not after "the whole notebook is done." A 30-second git add / commit / push every 15–20 minutes of real progress costs you almost nothing and caps your worst-case loss at ~15–20 minutes of work instead of hours.
   * Watch for the idle warning. Colab shows a disconnect countdown/pop-up when it's about to time you out — if you notice you've been reading/thinking for a while without running cells, that's your cue to push now, not "in a bit."
   * If you're stepping away for a while (lunch, switching tasks), push before you leave, even if the work feels "unfinished" — commit messages like "WIP: preprocessing, tokenizer not tested yet" are completely normal and expected in a shared branch.
There isn't a safer alternative to this — Drive-mounting would help persist a copy but you'd still need to explicitly save to it, same discipline, just an extra destination. Frequent small pushes is genuinely the standard practice here, not a workaround specific to your setup.

Q:
how do i change branch? do i need to do it from the start? i mean all the git cloning pulling and cell running?
A:
No — if you're switching branches within the same runtime session (same clone already on disk), it's just one command, and almost everything survives. You only need to redo the clone/setup if the runtime itself was wiped (disconnected/restarted).
Switching branches — the normal case
1. Check your current state first:
!git status


This tells you if you have uncommitted changes. You can't switch branches cleanly with uncommitted changes sitting around — Git will either block you or carry them over in a confusing way.
2. Save your current work before switching, if git status shows anything:
!git add .
!git commit -m "WIP before switching branches"
!git push origin yourname-feature


3. Switch branches:
!git checkout other-branch-name


If the branch only exists on GitHub and not yet on your local clone, use:
!git checkout -b other-branch-name origin/other-branch-name


("Create a local branch that tracks the one on GitHub.")
4. Get its latest changes:
!git pull origin other-branch-name


That's it — no re-cloning, no re-running pip install, no redoing notebooks 1–2.
Why so little needs to be redone
Think of git checkout as swapping which version of the files are visible — it doesn't touch the runtime itself. A few concrete examples:
   * src/ and notebooks/ files — update to match the new branch instantly.
   * Installed packages (torch, transformers, etc.) — stay installed. They're not part of the Git repo; they live separately on the runtime.
   * data/ folder — this is the one subtlety. Since data/ is .gitignore'd (not tracked by Git), switching branches does not touch it at all — it just stays sitting on disk, visible to whichever branch you're on. So if the new branch's code expects the same train.parquet/validation.parquet files, they're already there, no need to regenerate them.
When you do need to redo the full setup
Only when the runtime itself is gone — meaning the disk is wiped, not just "I want different code":
   * You got disconnected / hit the 90-minute timeout and reopened Colab later
   * You ran Runtime → Disconnect and delete runtime
   * You're starting in a brand-new Colab tab that was never connected to that clone
In that case, yes — full clone, pip install, mkdir data, run notebooks 1–2 again, same as your very first session. (Runtime → Restart session, by contrast, keeps the disk — covered this difference earlier when fixing the torchvision issue.)
Quick way to tell which situation you're in
!pwd
!git branch


If this runs without error and shows /content/nlp-ku-project with your branches listed, your runtime is still alive — just checkout and go. If you get a "no such file or directory" or similar, the disk is gone — do the full setup.

A:
There are two different ideas getting mixed together here: <UNK> and sentence-boundary tokens.
1. Do we put <UNK>, <s>, and </s> into every sequence?
No. They have different purposes.
<UNK>
<UNK> is a replacement for an unknown real token.
It only appears when a token isn't in the vocabulary.
For example:
Original:
["I", "like", "pizza"]


Vocabulary:
I, like, pizza, <UNK>, <s>, </s>
Nothing is unknown, so:
["I", "like", "pizza"]
But if pizza isn't in the vocabulary:
["I", "like", "<UNK>"]
So you don't automatically add <UNK> to every sentence.
________________


<s>
<s> means:
start of sentence
The language model adds it because the first real word doesn't have a previous word.
For a bigram:
<s> I like pizza
This allows the model to learn:
P(I | <s>)
In other words:
How likely is I to be the first word?
________________


</s>
</s> means:
end of sentence
For example:
<s> I like pizza </s>
This can allow a model to learn:
P(</s> | pizza)
meaning:
How likely is the sentence to end after pizza?

Bigram

Trigram

"she likes" → "pizza"

"the man" → "wrote"

So your trigram model has much less data for each context.
That's called data sparsity.
